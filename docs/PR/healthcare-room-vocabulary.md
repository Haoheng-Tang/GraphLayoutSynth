# Expand the default healthcare room vocabulary

Branch: `feat/healthcare-room-vocabulary` → `main`

## Summary

Expands the default config's canonical vocabulary from 4 user-facing room
types to 35 flat PascalCase healthcare types, spanning patient care,
on-stage/off-stage corridors, staff work/administration, clinical support,
staff/public/family amenity, vertical circulation, and building services.
Hierarchy is represented exclusively through `semantic_node_groups` — no
nested room-type IDs anywhere. Three vocabulary tiers are now explicit:
the **allowed canonical vocabulary** (recognized everywhere), the **default
essential generated mix** (what the base grammar actually produces), and
**optional room types** (valid on request via Program Requirements or
instruction-guided variants, not generated by default). Legacy `Corridor`,
`ClinicalSupport`, and `StaffSupport` remain allowed for compatibility.

The room-type catalog, Program Requirements validation, instruction-guided
variant prompts, `/suggest-next-room`, and debug artifacts all pick the new
vocabulary up automatically through the existing ConfigContract machinery —
no new endpoints, no schema changes, no new LLM calls.

## Vocabulary tiers

- **Allowed** (35 catalog types): everything in `allowed_node_types` minus
  structural `BuildingFloor`/`Zone`. Valid in Program Requirements, shown by
  `GET /program-requirements/room-types`, embedded in variant prompts.
- **Default essential mix** (~44 rooms/graph): 20–24 `PatientRoom`, 4
  `OnStageCorridor`, 1 `OffStageCorridor`, 2 each of `NurseStation`,
  `MedicationRoom`, `CleanUtility`, `SoiledUtility`, `EquipmentRoom`,
  `StorageRoom`, `Stair`, and 1 each of `StaffLounge`, `StaffToilet`,
  `PublicToilet`, `Elevator`, `MEPRoom`, `UtilityRoom`.
- **Optional** (16 types): `TeamRoom`, `Office`, `ConferenceRoom`,
  `NourishmentRoom`, `LinenRoom`, `RespiratoryTherapyRoom`, `PPEStorage`,
  `ConsultRoom`, `VisitorLounge`, `FamilyRoom`, `Dayroom`, `DiningRoom`,
  `ElectricalRoom`, `MechanicalRoom`, `TelecomRoom`, `Kitchen`.

Category names (`Administration`, `PatientSupport`, `PublicAmenity`,
`Infrastructure`, …) are semantic groups, not node types. Full reference:
`docs/ROOM_VOCABULARY.md`.

## Default grammar

Floor → 2 `WardZone` + 1 `ServiceZone` (Zone rules discriminated by
`zone_type` match attributes). Each ward: 2 on-stage corridors (chained,
first inherits zone connections), 10–12 patient rooms distributed across
both corridors via `balanced_each_to_one` (`max_sources_per_target: 6`) and
across nurse stations via `balanced_each_to_one`
(`max_sources_per_target: 12`), support rooms and stair `each_to_one` to
the corridor, patient-to-patient `adjacent_pairs` walls. The service zone:
1 off-stage corridor inheriting inter-zone links plus staff/public/service
rooms with corridor doors. `each_to_one` is kept wherever a single corridor
deliberately acts as the shared hub.

`room_mix_targets` was removed from the default config: its
patient/clinical/staff alias trio was built around the legacy vocabulary.
The section stays fully supported for configs that declare it.

## Code changes (all vocabulary-neutral)

- **Corridor detection is token-based** (`is_corridor_node_type` in
  `config_contract.py`, matching the contract's existing fallback-token
  rule): `validators.py` corridor-access checks, `ranking.py` room/corridor
  partitioning, `scoring.py`, and `review_summary.py` room-like filtering
  now treat any type containing "corridor" uniformly, replacing hardcoded
  `== "Corridor"` comparisons that would have failed every
  `OnStageCorridor` graph. Behavior for legacy `Corridor` graphs is
  unchanged (strictly widened matching).
- **`reachable_room_count_ranges` is zone-rule-aware**: each Zone-matching
  grammar rule's per-zone counts are multiplied by the count of
  floor-created zones whose attributes satisfy that rule's extra match
  constraints (e.g. `zone_type`), instead of multiplying the first Zone
  rule's counts by every zone. Old single-zone-rule configs produce
  identical results; the new two-ward-plus-service grammar gets accurate
  preflight ranges (PatientRoom 20–24, not a bogus 30–36).
- `ClinicalSupport`/`StaffSupport` stay separate everywhere they already
  appeared (review summaries untouched per guardrail); `Corridor` remains
  required in `allowed_node_types` by `config.py` and remains allowed.

## Known limitations

- Ranking's `_support_room_count` still matches the literal "support" token
  and legacy type names, so the `support_mix` metric contributes ~0 for
  default-generated graphs (uniform across candidates; ranking is
  unaffected in relative terms). Making it group-aware needs config
  threading through `compute_candidate_metrics` — deferred.
- Frontends anchored on legacy types (`Corridor`, `ClinicalSupport`) get
  empty suggestions from the new default generation and fall back locally,
  as the contract documents; payloads still validate unchanged.
- `Stair`/`Elevator` are graph nodes only — no egress, code-compliance, or
  travel-distance logic is implied.

## Non-goals

- No frontend code, no frontend add/remove of canonical types, no custom
  user-defined types, no Excel/CSV import, no area/width/height fields, no
  egress/code/travel-distance logic.
- No nested room hierarchy in generated graph JSON.
- No `/suggest-next-room` request-schema change, no active-variant behavior
  change, no new generator, no new LLM calls.
- No catalog metadata fields (`category`, `defaultIncluded`) — deferred to
  a coordinated frontend/backend branch since frontend tolerance for new
  response fields is not established.
